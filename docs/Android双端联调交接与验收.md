# Android × Web 双端联调交接与验收

2026-11-05：本轮交付 Android `0.1.60+61`。安装包及变更见 [0.1.60 更新说明](2026-11-05-0.1.60-更新说明.md)，构建记录见 [验证报告](../validation/release-0.1.60.md)。计划 `1/2 → 2/2`、真实接口和真机复验仍按下述流程执行，发布安装包不代表这些验收已经完成。

Web 对照版本：[d1459c2](https://github.com/WuChangqing1/PD-Rehab-Web/commit/d1459c2)。

本轮先验收 **同一个计划从 `1/2` 更新为 `2/2`，重复同步不新增快照**。Web 已发布计划进度和历史版本展示；包含进度上报修复的 Android APK 仍需真机复验。界面优化可以随后做。

## 1. 联调准备

- Web：[帕琴律动](https://ccqspace.site/pd-rehab/)。Android 的 HTTPS API 地址填写 `https://ccqspace.site/pd-rehab/api`。
- 安装确认包含 `daily_progress` 上报修复的 APK，记下版本号和构建号。
- 两端使用同一个测试患者。绑定前核对患者姓名、完整编号、本机档案归属，必要时通过接口对照患者 UUID。不要为方便测试将原有记录绑到无关患者。
- 约定测试日期和计划 ID。优先使用「123」舞蹈计划，设目标 `2 次`，避免已有同名计划混淆。
- 使用获准的测试账号和测试数据。账号密码、访问令牌、真实患者资料和私人录像不写入报告或截图。

## 2. 真机复测步骤

| 步骤 | Android 操作 | Web / API 预期 |
| --- | --- | --- |
| 1. 登录与绑定 | 登录并同步患者档案，确认患者后绑定 | 两端患者 UUID 一致，绑定成功 |
| 2. 第一次同步 | 完成第一次舞蹈练习，App 显示 `1/2`，手动同步 | 「随访与报告 → 软件端记录 → 训练计划」选对应日期，「123」显示 `1/2 次`。记下服务端记录 ID |
| 3. 第二次同步 | 完成第二次，App 显示 `2/2`，再次手动同步 | 列表仍只有同一条计划，当日显示 `2/2 次`。版本历史能找到 `1/2`，且两份快照记录 ID 不同 |
| 4. 重复同步 | 不改变计划，也不做新练习，直接再次同步 | 计划快照数量及记录 ID 不变；不因重试产生重复版本 |
| 5. 读取云端历史 | 在 Web 为同一测试患者准备一条可识别的测试记录；App 获取云端评估与训练历史 | 以同一条记录 ID 核对患者、类型、时间和内容；缓存总数只能作为辅助证据 |

## 3. 上传字段与定位方法

上传仍使用 `POST /api/integration/v1/records`，记录类型为 `TRAINING_PLAN`。检查上传的 `payload` 是否包含对应日期的进度：

```json
{
  "daily_progress": [
    {
      "local_date": "2026-11-03",
      "completed_units": 2,
      "target": 2,
      "target_type": "count"
    }
  ]
}
```

`local_date` 填计划实际归属的本地日期。次数目标的 `completed_units` 按次；分钟目标的 `target_type` 为 `minutes`，`completed_units` 按毫秒，`target` 按分钟。例如 `90000` 毫秒、目标 `2` 分钟，Web 应显示 `1.5/2 分钟`。未上传对应日期的有效进度时，Web 显示“进度未知”；明确上传 `0` 才显示零进度。

排查时按顺序看：**App 当前进度 → 上传请求 → Web 原始 JSON → Web 计划页**。App 显示 `2/2`、服务端原始快照没有对应进度时，检查 App 的快照构建与同步标记；原始快照已有正确进度时，核对 Web 选中日期、患者、设备档案及当前展示的快照 ID。

## 4. 第一轮通过后继续做什么

1. **补测失败场景。** 断网时练习应继续保存在本地，恢复网络后可重试；令牌过期后应提示重新登录；错误患者或无权限请求应被拦截；同一手机切换账号后不能看到上一账号的缓存。每项记录预期和实际行为，发现问题再修复。
2. **改 Android 展示。** 绑定后常驻显示患者姓名、完整编号和绑定状态。云端历史先展示中文类型、时间、状态和可读摘要，UUID 和原始数据放到详情。
3. **与 Web 约定离线版本顺序。** Web 在同组快照都带有效 `snapshot_revision` 时按源端修订号排序，否则标记“最近收到”。Android 如接入修订号，应为每个计划持久化递增版本：内容改变才递增，失败重试复用原版本和原记录 ID。新 APK 单独加字段不会让包含无版本旧快照的计划自动切换排序；历史兼容规则需双方确认后再上线。

协议细节见 [Web 计划进度说明](EXTERNAL_PLAN_PROGRESS.md)。
