# 新建计划页“无法读取提醒权限”排查

日期：2026-11-14。用户在真机报告：新建计划页通知提醒显示“无法读取提醒权限，请重试”，重试无效。检查对象为已发布的正式包 `0.1.70+71`。

后续修复交付：通知图标保留和通用权限引导已纳入本机 `0.1.71+72`，见 [更新说明](2026-11-14-0.1.71-更新说明.md) 与 [构建记录](../validation/release-0.1.71.md)。下方未构建/未复制等描述为排查各阶段的历史状态，不表示0.1.71缺少修复。

## 原因及证据

`_PlanReminderSetup.refresh()` 捕获 `PlanReminders.access()` 的所有异常，统一显示权限读取失败。实际调用先经过通知插件初始化，之后才检查系统通知、通知渠道与准时提醒权限。

初始化使用 `AndroidInitializationSettings('piano_icon')`。通知插件通过 Android `Resources.getIdentifier()` 按名称查找 drawable；找不到资源时返回 `invalid_icon` 并终止初始化。本机源码中存在 `res/drawable/piano_icon.xml`，但正式构建开启资源缩减，Dart 字符串引用不构成 Android 静态资源引用。

直接检查已分发 APK 的资源表，确认没有 `drawable/piano_icon`。原构建的 `build/app/outputs/mapping/release/resources.txt` 明确列出 `drawable:piano_icon ... is not reachable`。因此已发布包包含一个足以导致该提示的确定性缺陷；重试使用同一个缺少资源的 APK，不能修复。它并不等价于用户拒绝通知权限，也与 Web 服务、账号、网络无关。

## 修复

新增 `android/app/src/main/res/raw/keep.xml`，显式保留 `@drawable/piano_icon`。保留正常资源压缩及原有授权流程，不更改通知授权状态、计划数据或同步逻辑。

本轮是源码修复和正式构建验证，不变更版本号、不替换已经发布的 `0.1.70`、不覆盖 `releases` 中的已分发安装包、不推送 GitHub。修复必须通过后续新版本 APK 安装到手机才会生效，手机上的旧 APK 不会因本机代码变化自动更新。

## 本机验证

- 同发布参数重新构建 release 成功，日志 `build/reminder-icon-release-20261114-build.log`。
- 使用 aapt2 实际比较两份 APK 的资源表：已分发 0.1.70 缺少图标，修复后的正式构建包含 `resource 0x7f070014 drawable/piano_icon`。验证保持资源缩减开启，不是只检查 XML 文件存在。
- 现有提醒相关测试5项通过，覆盖权限状态、显式准时提醒设置、重复配置、通知调度和过期计划处理，日志 `build/reminder-icon-20261114-tests.log`。

## 设备复验

本轮 ADB 未发现连接设备，尚未取得用户手机上的 `invalid_icon` 日志或验证实际通知送达。更新修复包后应打开计划页，分别验证通知关闭、通知已允许、准时提醒未开启等状态，以及保存未来计划后的通知送达。系统通知权限、闹钟权限和手机省电限制仍需按实际状态处理；该资源修复不代表这些权限已授权。

## 后续真机排查：离开前台时无明显提醒

用户随后报告回桌面、锁屏、划掉最近任务以及强行停止四种情况下均未收到提醒。本次手机已连接，读取到 Vivo V2359A、Android 16，安装版本 `0.1.70+71`，安装更新时间为 2026-11-14 00:21:10。

只读系统证据：

- `POST_NOTIFICATIONS` 已允许，`SCHEDULE_EXACT_ALARM` 为 allow，后台运行 AppOp 为 allow，读取时应用未处于 stopped 状态。
- AlarmManager 记录琴伴的 `ScheduledNotificationReceiver` 曾被唤醒1次。
- NotificationManager 累计接受并发布琴伴通知2次，未阻止通知（`numBlocked=0`），提示打断数为0（`numInterrupt=0`）。该累计数据不能单独证明四种后台场景全部通过。
- 应用级设置为 `isShowHeadsUp=false`、`isShowKeyguard=false`，即悬浮/锁屏通知关闭；通知渠道本身 importance=4。现有 App 检查全局通知、渠道级别和精确闹钟权限，无法仅凭这些公开状态判定厂商独立的悬浮/锁屏开关。

已打开琴伴的系统通知设置，请用户开启悬浮及锁屏通知，并用未来约2分钟、尚未完成的计划验证回桌面后的触发。此时仍在等待操作及实际送达验证，未记录为通过。

强行停止需与普通后台区分：Android 15 起会取消被强行停止应用的 PendingIntent；Android 16 同样不能承诺强停后的本地计划通知。重新主动打开应用后，现有流程会重新调度未来计划。不能通过常驻服务、绕过强停或修改用户授权来承诺四种状态均送达。

依据：[Android 官方强行停止行为说明](https://developer.android.com/about/versions/15/behavior-changes-all#stopped-state)、[vivo 官方通知设置说明](https://kefu.vivo.com.cn/robot/imgmsgData/3dfcdb616d0542b4baa4e9ead6d75c5e/index_1.html)。

### 00:29 回桌面实测：系统冻结阻止提醒

用户完成开启悬浮与锁屏通知。00:28再次读取到 `isShowHeadsUp=true`、`isShowKeyguard=true`，系统已登记一条 00:29 的 `RTC_WAKEUP` 提醒，`window=0`、`exactAllowReason=permission`、flags=0x5；手机前台为桌面 Launcher，琴伴退居后台。

00:28:27.884，AlarmManager 的琴伴 UID 历史出现 `Reason=frozen`，快照对应 `ScheduledNotificationReceiver`。00:29:20时 NotificationManager 的累计通知数量仍为2，未新增本次通知，琴伴进程仍存在，应用 stopped=false。因此本次未送达具有系统冻结的直接证据，不能仅归因于通知横幅关闭，也不是缺少准时提醒权限。

已打开琴伴应用信息，等待用户为琴伴设置允许后台活动/后台高耗电及自启动后复验。本次不通过 ADB 改写全局省电、冻结策略或隐藏权限，也不添加用于规避系统策略的常驻服务。通知显示开关已开启，但目前尚不能把后台、锁屏、划掉最近任务记为通过。

### 放行后台耗电后的结果

用户报告已调整后台设置后，第二次测试仍在00:31:38.707出现新的 `Reason=frozen`，通知数量没有增加。随后使用 computer-use 查看真机投屏，沿“琴伴应用信息 → 电量 → 后台耗电管理”核实：实际仍选中“智能控制后台耗电”。将其切换为“允许后台耗电”，并通过页面蓝色选中状态确认变更生效；没有变更其他应用或全局省电策略。

之后用户明确反馈：“我刚刚已经测试了，可以了”。只读系统复核显示：琴伴已发布通知数从2增加到3，AlarmManager 的提醒唤醒数从1增加到2。记录为本机此次用户实测恢复，并有新增通知与闹钟触发的系统证据支持。

该结果不扩展为所有 Android 品牌、长时间待机、重启、最近任务划除、强行停止均已通过。特别是强行停止仍受 Android 系统限制，需主动重新打开 App 恢复未来计划调度。本次用户实测未详细逐项区分所有场景，不写成四种场景全部通过。

交付提示：本次后台问题通过该手机的通知显示和后台耗电设置解决，无新增常驻服务或后台绕过代码。后续产品可增加“系统通知设置/后台提醒设置说明”入口，避免仅凭通知总开关及精确闹钟权限把厂商环境标为完全就绪。通知图标保留配置仍是待发布源码修复；本次未上传新 APK 或推送仓库。

## 最小设置范围核对

区分 Android 运行时权限、厂商后台策略与通知显示选项，不将所有选项都描述为必须授权。

| 设置 | 作用及必要范围 |
|---|---|
| 允许通知，且训练计划提醒渠道未关闭 | Android 13及以上发布普通提醒的必要条件。 |
| 本机“允许后台耗电” | 本次 Vivo 退后台冻结的直接相关设置；切换后实测恢复。不是所有品牌手机通用的额外 Android 权限。 |
| 闹钟和提醒/准时提醒 | 要按设定时间精确触发时开启。现有代码在未允许时退回非精确闹钟，并非完全不能发通知，但可能延迟。 |
| 悬浮通知 | 希望在其他页面上方弹出提示时开启；不是通知进入通知栏的必要条件。 |
| 锁屏通知 | 希望在锁屏显示提醒时开启；不是所有通知发布的必要条件。 |
| 自启动、关联启动 | 厂商后台/进程清理与重启恢复的兼容选项。刚才实测未逐项关闭它们，不能据此确认两项都必需，也不能承诺在该机上关闭后仍通过全部场景。 |
| 相机、麦克风、定位、通讯录、悬浮窗、无障碍 | 当前本地计划通知不依赖这些权限。悬浮通知与“显示在其他应用上层”的悬浮窗权限不同。 |

日常退后台的最小建议以“允许通知 + 本机放行后台耗电”为基础；对准时提醒再加闹钟权限，对横幅/锁屏显示分别增加对应选项。这是按代码调用、Android文档及本次观察归类的最小建议，不是对当前手机所有开关逐一消融后的完整证明。没有为此次核对改变手机已恢复工作的权限配置。

参考：[Android 通知权限](https://developer.android.com/develop/ui/compose/notifications/notification-permission)、[Android 闹钟调度与精确/非精确区别](https://developer.android.com/develop/background-work/services/alarms)、上文 vivo 官方通知说明。

后续用户进一步测试明确反馈，自启动与允许通知需要开启；因此不再将“只放行后台耗电即可”作为该机型的完整结论。已按用户要求开发通用 Android 机型的一键连续设置引导，包含自启动人工确认及不同品牌回退，详见 [通用机型提醒授权引导](2026-11-14-通用机型提醒授权引导.md)。前述最小配置为当时观察，不能代替这一轮补充实测。
