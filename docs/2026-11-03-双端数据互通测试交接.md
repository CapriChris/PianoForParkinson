## 已发现的问题与处理建议

1. **本次自动化执行受阻。** Windows 电脑操作工具在切换到 Edge 时提示无法可靠识别当前浏览器 URL 并停止。请人工确认浏览器地址和登录状态后重新开始，或排查该工具对当前 Edge 窗口的识别。该现象不构成 Web 产品缺陷的证据。
2. **患者身份展示不够清晰。** 本次经用户确认数据归属后，虚拟患者绑定成功。建议页面完整显示患者编号和绑定状态，方便操作人员核对。
3. **记录内容仍待逐项核对。** 当前已核对 Web 列表展示及服务端数量，尚需核对具体记录的原始字段。

1. 在手机登录云端服务，在 Web 端打开同一测试环境。双方确认测试患者 UUID 和设备档案归属。

## 计划自动进度同步修复（Android 待真机复验）

用户复现“123”舞蹈计划从 1/2 完成到 2/2 后，仅看到新增舞蹈训练，计划进度未更新。根因是 App 计划进度通过 `TrainingScheduleRepository.automaticProgressFor` 根据当天已保存且通过完整性检查的训练自动计算，并不要求产生 `plan_links`。原同步只发送计划行、持久化日程和手动链接，自动进度变化不会改变计划快照的哈希。

Android 已在训练计划快照中新增 `daily_progress` 数组，包含 `local_date`、`completed_units`、`target` 和 `target_type`。数值复用 App 现有自动进度计算规则，舞蹈分钟目标的 completed_units 以毫秒计，次数目标按次计。快照哈希包含该数组，进度发生变化后生成新的追加式计划版本；内容未变重复同步沿用既有标记。保留原 record、occurrences 与记录类型，服务器不需要新增入参字段解析即可保留 payload。

Web 需要按计划 ID 和最新版本选择展示，并从 `daily_progress` 中读取对应日期的完成量和目标。分钟目标需按毫秒转换，不能将计划的日期当作创建时间。历史记录无 daily_progress 时显示未知或按版本约定处理；计划快照为追加式版本，不能直接把每个版本当成独立计划统计。修改前后、跨天、停用及删除计划的语义和历史回看需双方进一步约定。

回归测试使用真实 SQLite 与实际进度计算，验证舞蹈计划从 1/2 到 2/2 会生成新计划版本，内容不变的第三次同步不重复上传。尚需安装新 APK，对“123”手动同步后核对服务端 raw payload 和 Web 页面；目前 Web 不会自动把新增字段渲染成进度。
